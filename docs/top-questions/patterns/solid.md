# SOLID — пять принципов на пальцах

**SOLID** — пять принципов проектирования, которые помогают писать код, который
**легко менять и расширять**, а не переписывать. Это аббревиатура из пяти букв.
Разберём каждый простым языком с примером.

## S — Single Responsibility (единственная ответственность)

**У класса должна быть одна причина для изменения** — то есть он отвечает за что-то
одно.

Плохо: класс `User`, который и хранит данные, и сохраняет себя в БД, и шлёт письма.
Изменится способ отправки писем — трогаем класс пользователя. Хорошо: разделить на
`User`, `UserRepository`, `EmailService` — каждый про своё.

## O — Open/Closed (открыт для расширения, закрыт для изменения)

**Добавлять новое поведение — не переписывая старый код.** Новую функциональность
добавляем через новый класс, а не правкой существующего.

```java
// Плохо: при новом типе оплаты лезем в этот if
if (type.equals("card")) { ... } else if (type.equals("sbp")) { ... }

// Хорошо: новый способ = новый класс, реализующий интерфейс
interface PaymentMethod { void pay(); }
class CardPayment implements PaymentMethod { ... }
class SbpPayment implements PaymentMethod { ... }   // добавили, старое не тронули
```

## L — Liskov Substitution (подстановка Барбары Лисков)

**Наследник должен работать всюду, где ожидается родитель, не ломая логику.** Если
код работает с `Bird`, то любой наследник `Bird` не должен преподносить сюрпризов.

Классический анти-пример: `Penguin extends Bird` с методом `fly()`. Пингвин не
летает — если подставить его туда, где ждут летающую птицу, всё сломается. Значит,
иерархия построена неверно.

## I — Interface Segregation (разделение интерфейсов)

**Лучше несколько узких интерфейсов, чем один огромный.** Класс не должен зависеть от
методов, которые ему не нужны.

Плохо: интерфейс `Worker` с `work()` и `eat()`. Робот-рабочий вынужден реализовать
`eat()`, который ему не нужен. Хорошо: разделить на `Workable` и `Eatable`.

## D — Dependency Inversion (инверсия зависимостей)

**Зависеть от абстракций (интерфейсов), а не от конкретных классов.** Классы верхнего
уровня не должны быть жёстко привязаны к конкретной реализации.

```java
// Плохо: сервис намертво привязан к конкретной БД
class OrderService {
    private final PostgresRepository repo = new PostgresRepository();
}

// Хорошо: зависит от интерфейса, реализацию подставят снаружи (DI)
class OrderService {
    private final OrderRepository repo;   // интерфейс
    OrderService(OrderRepository repo) { this.repo = repo; }
}
```

Именно этот принцип реализует [DI в Spring](../spring/ioc-di.md): контейнер
подставляет реализацию, а код зависит от интерфейса.

## Что запомнить

- **S** — один класс = одна ответственность.
- **O** — расширять новым кодом, не меняя старый.
- **L** — наследник заменяет родителя без сюрпризов.
- **I** — узкие интерфейсы вместо одного большого.
- **D** — зависеть от интерфейсов, а не от конкретных классов (это и есть DI).
- Общая цель — код, который **легко менять и расширять**.
