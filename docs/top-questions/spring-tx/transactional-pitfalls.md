# Когда `@Transactional` не срабатывает

Очень частый и коварный вопрос. `@Transactional` может **молча не сработать** — код
выполнится, но без транзакции, и данные не откатятся. Почти все причины — из-за того,
что аннотация работает через **прокси**. Разберём главные случаи.

## Почему прокси — источник всех бед

Напомним: Spring оборачивает бин в [прокси](../spring/aop.md), и транзакция
открывается, только когда вызов проходит **через эту обёртку** — то есть при вызове
**извне**, от другого бина. Если вызов идёт мимо прокси — транзакции не будет.

## Причина 1: self-invocation (вызов своего же метода)

Самая знаменитая ловушка. Метод бина вызывает **другой метод того же бина** напрямую:

```java
@Service
class OrderService {

    public void process() {
        save();   // вызов через this — МИМО прокси!
    }

    @Transactional
    public void save() { ... }   // транзакция НЕ откроется
}
```

Вызов `save()` — это на самом деле `this.save()`, он идёт напрямую к объекту, а не
через прокси. Прокси не видит вызов → транзакция не открывается.

```mermaid
flowchart LR
    Ext["Внешний вызов"] --> Proxy["Прокси (открывает транзакцию)"]
    Proxy --> Real["process()"]
    Real -->|"this.save() мимо прокси"| Save["save() без транзакции"]
```

**Как чинить:** вынести `save()` в **другой бин**, либо перестроить так, чтобы
транзакция была на внешнем методе.

## Причина 2: не `public` метод

Прокси Spring перехватывает только **`public`**-методы. `@Transactional` на
`private`, `protected` или package-private методе **игнорируется**.

## Причина 3: исключение поймано внутри

Если внутри метода исключение **перехвачено** `try/catch` и не проброшено дальше,
прокси о нём не узнает и сделает **commit**, а не rollback:

```java
@Transactional
public void save() {
    try {
        repo.save(...);   // упало
    } catch (Exception e) {
        log.error("ошибка", e);   // проглотили — прокси думает, что всё ок → commit
    }
}
```

## Причина 4: откат только на unchecked-исключениях

По умолчанию Spring откатывает транзакцию **только на `RuntimeException` и `Error`**.
Если бросить **проверяемое** (checked) исключение — отката **не будет**. Подробно —
[исключения и откат](rollback-exceptions.md). Лечится `rollbackFor`.

## Причина 5: вызов на «сыром» объекте

Если создать бин через `new` самому (а не получить из контейнера), прокси не будет
вообще — это уже не управляемый Spring объект.

## Что запомнить

Почти всё сводится к «вызов пошёл мимо прокси» или «прокси не увидел ошибку»:

- **self-invocation** — внутренний вызов `this.method()` не проходит через прокси;
- метод **не `public`**;
- исключение **проглочено** внутри `try/catch`;
- брошено **checked**-исключение (нет `rollbackFor`);
- бин создан через `new`, а не взят из контейнера.
