# Как Hibernate работает с БД на низком уровне

Полезно понимать, что Hibernate делает «под капотом»: он не бежит в базу на каждый
твой вызов, а копит изменения и применяет их пачкой в нужный момент. Ключевые
понятия — **dirty checking**, **flush** и **отложенность** запросов.

## Hibernate не спешит в БД

Когда ты меняешь managed-сущность, Hibernate **не** делает `UPDATE` сразу. Он
запоминает изменения в [Persistence Context](entity-lifecycle.md) и откладывает
поход в базу до **flush**. Это позволяет объединять изменения и делать меньше
запросов.

```java
@Transactional
public void update() {
    User u = repo.findById(1L).orElseThrow();  // SELECT
    u.setName("Аня");                           // пока НИКАКОГО UPDATE
    u.setAge(25);                               // и здесь тоже нет
    // UPDATE полетит один раз — на flush (обычно перед commit)
}
```

## Dirty checking — автоматическое отслеживание изменений

**Dirty checking** («проверка на грязь») — механизм, которым Hibernate находит, что
изменилось. Работает так:

1. когда сущность попадает в контекст, Hibernate запоминает её **исходное** состояние
   (снимок полей);
2. перед flush он **сравнивает** текущее состояние каждого объекта со снимком;
3. для полей, которые изменились, генерирует `UPDATE`.

Именно поэтому не нужно вызывать `save()` для managed-объекта — Hibernate сам увидит
разницу.

```mermaid
flowchart LR
    L["Загрузили: снимок {name: Ян, age: 20}"] --> C["Изменили: {name: Аня, age: 25}"]
    C --> F["flush: сравнение со снимком"]
    F --> U["изменилось → UPDATE"]
```

## Flush — когда изменения уходят в БД

**Flush** — момент, когда накопленные изменения (`INSERT`/`UPDATE`/`DELETE`)
**отправляются** в базу. Flush происходит:

- **перед commit** транзакции (главный случай);
- **перед запросом**, если он может задеть несохранённые изменения (чтобы запрос
  увидел актуальные данные);
- при явном вызове `flush()`.

Важно: **flush ≠ commit**. Flush отправляет SQL в БД, но транзакция ещё не
зафиксирована — её ещё можно откатить. Commit завершает транзакцию.

## Как формируется SQL

- Hibernate строит SQL из маппинга сущностей (JPQL → SQL под конкретную БД через
  «диалект»).
- Часто использует **prepared statements** (параметры через `?`) — это и защита от
  инъекций, и переиспользование плана запроса.
- Может **батчить** несколько `INSERT`/`UPDATE` в один пакет
  (`hibernate.jdbc.batch_size`) — меньше round-trip к базе.

## Что запомнить

- Hibernate **откладывает** запись: копит изменения и применяет на flush.
- **Dirty checking** — сравнивает объект со снимком исходного состояния и сам делает
  `UPDATE` изменённых полей (поэтому `save()` для managed не нужен).
- **Flush** отправляет SQL в БД (перед commit / перед запросом / вручную), но это ещё
  не commit — откат возможен.
