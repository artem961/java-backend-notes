# Запуск и compose

Собрать образ — половина дела. Дальше контейнер нужно **запустить**, дать ему порты,
данные и настройки, а часто — поднять сразу несколько связанных сервисов
(приложение + база + Kafka). Для одного контейнера есть `docker run`, для набора —
`docker compose`.

## docker run и его флаги

```bash
docker run -d \
  --name myapp \
  -p 8080:8080 \
  -e SPRING_PROFILES_ACTIVE=prod \
  -v mydata:/var/lib/data \
  myapp:latest
```

Что здесь важно понять:

- **`-p 8080:8080`** — проброс порта: `хост:контейнер`. Контейнер изолирован, и
  снаружи к нему не достучаться, пока порт явно не пробросили. Левое число — порт на
  хосте, правое — внутри контейнера.
- **`-e`** — переменная окружения. Основной способ **конфигурировать** контейнер
  снаружи: один и тот же образ запускают с разными настройками (профиль Spring,
  строка подключения к БД, пароли).
- **`-v`** — том (volume). Без него все данные внутри контейнера **исчезают при его
  удалении** — контейнер эфемерен. Том хранит данные на хосте отдельно от жизни
  контейнера (о томах ниже).
- **`-d`** — в фоне (detached); **`--name`** — понятное имя вместо случайного.

## Тома: данные переживают контейнер

Файловая система контейнера временная: удалили контейнер — потеряли всё, что он
записал. Для базы данных это неприемлемо. **Том** отвязывает данные от контейнера:

- **named volume** (`-v mydata:/path`) — Docker хранит данные у себя, переживают
  пересоздание контейнера; так обычно держат данные БД;
- **bind mount** (`-v ./config:/app/config`) — прокинуть конкретную папку хоста
  внутрь; удобно для конфигов и локальной разработки.

## Сети

Контейнеры по умолчанию в изолированной сети Docker и **видят друг друга по имени**.
Если приложение и база в одной сети, приложение подключается к базе по имени
контейнера (`jdbc:postgresql://db:5432/...`), а не по `localhost`. Это ключевой
момент: внутри compose-сети `localhost` — это сам контейнер, а не соседний.

## docker compose

Запускать вручную несколько `docker run`, прокидывать порты и связывать сети — долго
и неповторяемо. **Compose** описывает весь набор сервисов в одном YAML-файле, и всё
поднимается одной командой.

```yaml
services:
  app:
    build: .
    ports:
      - "8080:8080"
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/mydb
    depends_on:
      - db

  db:
    image: postgres:16
    environment:
      POSTGRES_DB: mydb
      POSTGRES_PASSWORD: secret
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:
```

```bash
docker compose up -d      # поднять весь набор
docker compose logs -f    # смотреть логи
docker compose down       # остановить и убрать
```

Что даёт: приложение обращается к базе по имени `db` (общая сеть создаётся
автоматически), данные базы лежат в томе `pgdata`, `depends_on` задаёт порядок
старта. Для разработчика это главный сценарий Docker — **одной командой поднять всё
окружение приложения** локально: базу, брокер, кеш, само приложение.

!!! note "depends_on ≠ готовность"
    `depends_on` дожидается только **старта** контейнера базы, а не её готовности
    принимать соединения. Postgres может ещё инициализироваться. Поэтому приложение
    должно уметь переживать недоступность зависимостей на старте (ретраи подключения)
    или используют healthcheck — иначе приложение падает при первом запуске.

## Как ответить на интервью

Коротко: один контейнер запускаю через `docker run`, ключевые флаги — `-p` (проброс
порта хост:контейнер, иначе снаружи не достучаться), `-e` (переменные окружения —
основной способ конфигурировать образ снаружи), `-v` (том, чтобы данные пережили
удаление контейнера — сам контейнер эфемерен). Когда сервисов несколько — приложение,
база, Kafka — использую **docker compose**: весь набор описан в одном YAML и
поднимается одной командой `up`. Внутри compose-сети контейнеры видят друг друга по
имени сервиса, поэтому приложение ходит в базу по `db:5432`, а не по `localhost`. На
практике это мой основной способ поднять локально всё окружение приложения. Одна
тонкость — `depends_on` ждёт старта контейнера, но не готовности базы принимать
соединения, поэтому приложению нужны ретраи подключения.
