# GitHub Actions и GitLab CI

Пайплайны описывают текстом (YAML) прямо в репозитории, и система CI/CD выполняет их на
события. Самые распространённые системы — **GitHub Actions** и **GitLab CI**. Для
junior-а важно узнавать такой конфиг, понимать его структуру и уметь прочитать, что
пайплайн делает, — а не писать сложные пайплайны наизусть.

## Общая идея

У всех систем CI/CD один принцип:

- конфиг лежит **в самом репозитории** (пайплайн как код, версионируется вместе с
  проектом);
- он **запускается на событие** — пуш, pull/merge request, тег, по расписанию;
- состоит из **шагов**, которые выполняются на чистой машине-раннере (часто прямо в
  Docker-контейнере), поэтому сборка воспроизводима и не зависит от чьей-то локальной
  машины.

Различаются в основном синтаксисом и терминологией — поняв одну, легко читаешь другую.

## GitHub Actions

Конфиг — файлы в `.github/workflows/*.yml`. Терминология: **workflow** (весь процесс) →
**jobs** (задачи, могут идти параллельно) → **steps** (шаги внутри job). Готовые
переиспользуемые шаги называются **actions** (например, `actions/checkout`).

```yaml
name: CI
on: [push, pull_request]      # на какое событие запускать

jobs:
  build:
    runs-on: ubuntu-latest    # раннер
    steps:
      - uses: actions/checkout@v4          # забрать код
      - uses: actions/setup-java@v4        # поставить JDK
        with:
          java-version: '21'
      - run: mvn -B verify                 # собрать и прогнать тесты
```

Именно GitHub Actions собирает и деплоит **этот конспект** — по пушу в `main` гоняет
`mkdocs build --strict` и публикует на GitHub Pages.

## GitLab CI

Конфиг — один файл `.gitlab-ci.yml` в корне. Терминология: **pipeline** → **stages**
(этапы идут по порядку) → **jobs** (внутри этапа, параллельно).

```yaml
stages: [build, test]

build:
  stage: build
  image: maven:3.9-eclipse-temurin-21
  script:
    - mvn -B package

test:
  stage: test
  image: maven:3.9-eclipse-temurin-21
  script:
    - mvn -B test
```

Идея та же: этапы по порядку, задачи внутри этапа, каждый job выполняется в указанном
Docker-образе.

## Секреты

Пароли, токены, ключи для деплоя **не хранят в конфиге** — они лежат в защищённых
переменных/секретах системы CI (Settings → Secrets в GitHub, CI/CD Variables в GitLab) и
подставляются в пайплайн на лету. В YAML попадает только ссылка на секрет, не его
значение. Это стандартное правило безопасности пайплайнов.

## Как ответить на интервью

Коротко: пайплайны описываются YAML прямо в репозитории, самые распространённые системы —
GitHub Actions и GitLab CI. Принцип у всех одинаковый: конфиг лежит в репозитории как
код, запускается на событие (пуш, PR, тег) и выполняется шагами на чистом раннере, часто
в Docker-контейнере, поэтому сборка воспроизводима. В GitHub Actions это workflow → jobs
→ steps в `.github/workflows`, в GitLab CI — pipeline → stages → jobs в `.gitlab-ci.yml`;
различаются в основном синтаксисом, поняв одну — читаешь другую. Секреты для деплоя в
конфиг не пишут — они в защищённых переменных CI и подставляются на лету. Сам сложные
пайплайны не настраивал, но конфиг прочитать и понять, что он делает, могу — и знаю, что
этот конспект деплоится через GitHub Actions.
