# Повседневная работа

Набор команд и приёмов, которыми пользуешься каждый день. Здесь не про редкие
случаи, а про обычный цикл: внести изменения, зафиксировать, отправить.

## Базовый цикл

```bash
git status                 # что изменено, что в staging
git add file.java          # добавить конкретный файл в коммит
git commit -m "Сообщение"  # зафиксировать
git push                   # отправить в удалённый репозиторий
```

- `git status` — первое, что смотришь: какие файлы изменены, что уже в индексе.
- `git add <файл>` — добавляй **конкретные** файлы. `git add .` затягивает всё
  подряд, включая случайный мусор, — так легко закоммитить лишнее.
- `git diff` — посмотреть, **что именно** изменилось (до `add`); `git diff --staged`
  — что уже в индексе.
- `git log --oneline` — компактная история коммитов.

## Хороший коммит

- **Атомарный** — одно логическое изменение на коммит. Не мешать в кучу правку
  бага и рефакторинг: так историю проще читать и откатывать.
- **Осмысленное сообщение** — что и зачем, а не «фикс», «ещё правки». Часто в
  повелительном наклонении: «Добавить валидацию email».

## Работа с ветками

```bash
git switch -c feature/login   # создать ветку и перейти в неё
git switch main               # переключиться на существующую
git branch                    # список веток
```

Под каждую задачу — своя ветка от `main`. Так работа изолирована, `main` остаётся
рабочим, а готовое вливается через pull request.

## Обновиться и влить чужое

```bash
git pull                 # забрать свежие коммиты из удалённого
```

`git pull` подтягивает чужие изменения. Если вы с кем-то правили одно место —
возможен **конфликт слияния**: Git не может сам решить, чью версию взять, и
помечает спорные места в файле. Их разрешают руками, выбирая правильный вариант,
затем `add` + `commit`.

## `.gitignore`

Файл `.gitignore` перечисляет, что Git **не должен** отслеживать: собранные
артефакты (`target/`, `build/`), настройки IDE (`.idea/`), секреты, временные
файлы. Без него в репозиторий легко попадает лишнее.

## Как ответить на интервью

Коротко: повседневный цикл — `git status` посмотреть изменения, `git add` на
**конкретные** файлы (не `git add .` вслепую, чтобы не закоммитить лишнее),
`git commit` с осмысленным сообщением, `git push`. Коммиты держу атомарными — одно
логическое изменение. Под задачу завожу ветку от `main` через `git switch -c`,
готовое вливаю через pull request. Чужое подтягиваю `git pull`; если правили одно
место — конфликт слияния, Git помечает спорные строки, разрешаю руками и коммичу.
Что не должно попадать в репозиторий (`target/`, `.idea/`, секреты) — держу в
`.gitignore`.
