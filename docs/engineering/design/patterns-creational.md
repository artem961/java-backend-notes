# Порождающие паттерны

Паттерны — типовые решения повторяющихся задач проектирования. Это не готовый
код, а **проверенный способ** организовать классы под конкретную проблему.
Порождающие паттерны отвечают за то, **как создаются объекты**. Разберём самые
востребованные.

## Factory Method / фабрика

**Проблема:** создание объекта завязано на конкретный класс (`new CardPayment()`)
и раскидано по коду; чтобы добавить новый тип, приходится править везде.

**Решение:** прячем создание за методом/классом-фабрикой, который по параметру
возвращает нужную реализацию интерфейса.

```java
interface Payment { void pay(); }

class PaymentFactory {
    Payment create(String type) {
        return switch (type) {
            case "card" -> new CardPayment();
            case "sbp"  -> new SbpPayment();
            default -> throw new IllegalArgumentException(type);
        };
    }
}
```

- **Плюс:** логика создания в одном месте; клиент работает с интерфейсом и не
  знает про конкретные классы (слабая связанность, принцип Open/Closed).
- **Минус:** лишний уровень косвенности; для одного-двух типов может быть
  избыточно.

## Builder / строитель

**Проблема:** у объекта много полей, часть необязательные. Конструктор с десятью
аргументами нечитаем (`new User("a", null, null, 5, true, ...)`), а телескопы из
перегрузок — боль.

**Решение:** пошаговое построение через цепочку методов, в конце — `build()`.

```java
User user = User.builder()
    .name("Иван")
    .email("ivan@mail.ru")
    .active(true)
    .build();
```

- **Плюс:** читаемо, порядок аргументов не важен, легко собирать неизменяемые
  объекты. В Java часто генерируется аннотацией Lombok `@Builder`.
- **Минус:** больше кода (если не Lombok); для объекта с двумя полями не нужен.

## Singleton / одиночка

**Проблема:** нужен ровно один экземпляр на всё приложение (пул соединений,
конфиг, кэш).

**Решение:** класс сам контролирует, что экземпляр создаётся один раз, и отдаёт
его всем.

- **Важно:** в Spring этим занимается контейнер — **бины по умолчанию
  синглтоны** (один экземпляр на контекст). Руками писать классический синглтон
  почти не нужно.
- **Минус:** глобальное состояние усложняет тестирование, а «ручной» синглтон
  легко сделать небезопасным в многопоточке.

## Как это соотносится со Spring

На практике порождающие паттерны в Spring чаще всего **берёт на себя фреймворк**:
контейнер создаёт бины (фабрика), управляет единственностью (синглтон), а Lombok
даёт билдеры. Понимать паттерны нужно, чтобы видеть, что именно за тебя делает
Spring.

## Как ответить на интервью

Коротко: порождающие паттерны про создание объектов. **Фабрика** прячет `new` за
методом, возвращающим реализацию по параметру, — клиент зависит от интерфейса, а
не от конкретных классов. **Строитель** собирает объект с многими полями пошагово
через цепочку методов, читаемо и удобно для неизменяемых объектов (в Java —
Lombok `@Builder`). **Синглтон** гарантирует один экземпляр; в Spring это делает
контейнер — бины по умолчанию синглтоны, руками писать не нужно. Главная мысль —
многое из этого в Spring берёт на себя фреймворк.
