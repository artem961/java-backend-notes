# Структурные паттерны

Структурные паттерны — про то, **как объекты и классы собираются в более крупные
структуры**, оставаясь гибкими. Здесь самые полезные на практике: их постоянно
встречаешь в Spring и стандартной библиотеке.

## Adapter / адаптер

**Проблема:** есть класс с нужной логикой, но его интерфейс не совпадает с тем,
что ждёт твой код (например, сторонняя библиотека).

**Решение:** обёртка, которая переводит один интерфейс в другой.

- Аналогия — переходник для розетки: вилка та же, форма разная.
- Типично при интеграции со сторонним API: адаптер прячет чужой интерфейс за
  твоим, и остальной код работает с привычным контрактом.

## Decorator / декоратор

**Проблема:** нужно **добавить поведение** объекту, не меняя его класс и не плодя
наследников под каждую комбинацию.

**Решение:** обёртка того же интерфейса, которая добавляет что-то до/после вызова
и делегирует основному объекту.

```java
interface DataSource { void write(String data); }

class EncryptedDataSource implements DataSource {
    private final DataSource origin;
    EncryptedDataSource(DataSource origin) { this.origin = origin; }
    public void write(String data) {
        origin.write(encrypt(data)); // добавили шифрование поверх
    }
}
```

- **Плюс:** поведение собирается послойно в рантайме (шифрование + сжатие +
  логирование), без взрыва иерархии наследования. Это композиция вместо
  наследования в чистом виде.
- Пример из JDK — обёртки потоков: `new BufferedReader(new InputStreamReader(...))`.

## Proxy / заместитель

**Проблема:** нужно контролировать доступ к объекту — добавить проверку,
кэширование, отложенную инициализацию или удалённый вызов — не меняя сам объект.

**Решение:** объект-заместитель с тем же интерфейсом стоит «перед» настоящим и
решает, что делать до/вместо вызова.

- **Ключевой для Spring:** на прокси построены `@Transactional`, `@Cacheable`,
  Spring AOP и Security. Spring оборачивает бин прокси, и тот открывает
  транзакцию/проверяет права до вызова твоего метода.
- Отличие от декоратора: декоратор **добавляет функциональность**, прокси
  **управляет доступом** — интерфейс тот же, но цель разная.

## Facade / фасад

**Проблема:** подсистема состоит из многих классов, и клиенту приходится знать
их все и правильный порядок вызовов.

**Решение:** один простой интерфейс-«фасад», за которым спрятана сложность.

- По сути этим занимается сервисный слой: `OrderService.placeOrder()` внутри
  дёргает репозиторий, оплату, уведомления — а контроллер видит один метод.

## Как ответить на интервью

Коротко: структурные паттерны — про сборку объектов в структуры. **Адаптер** —
переходник между несовместимыми интерфейсами (обёртка над чужим API).
**Декоратор** — обёртка того же интерфейса, добавляющая поведение послойно без
наследования (пример — потоки в JDK). **Прокси** — заместитель с тем же
интерфейсом, контролирующий доступ; на нём в Spring стоят `@Transactional`,
`@Cacheable`, AOP и Security. **Фасад** — простой интерфейс поверх сложной
подсистемы, по сути роль сервисного слоя. Декоратор добавляет функциональность,
прокси управляет доступом — вот их различие.
