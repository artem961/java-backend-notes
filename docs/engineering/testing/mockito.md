# Моки и Mockito

Чтобы проверить класс **в изоляции**, его зависимости нужно чем-то заменить —
иначе unit-тест потащит за собой БД, сеть и чужую логику. Для этого используют
**моки**, а в Java — библиотеку Mockito.

## Зачем мок

Пусть `OrderService` зависит от `OrderRepository` и `PaymentClient`. В unit-тесте
нам не нужна настоящая база и настоящий платёжный сервис — нужно проверить
**логику самого `OrderService`**. Поэтому зависимости подменяем **моками** —
объектами-заглушками, поведением которых мы управляем.

```java
@Test
void placesOrder() {
    OrderRepository repo = mock(OrderRepository.class);
    when(repo.save(any())).thenReturn(new Order(1L));   // задали поведение

    OrderService service = new OrderService(repo);
    Order order = service.place(...);

    assertEquals(1L, order.getId());
    verify(repo).save(any());   // проверили, что метод был вызван
}
```

## Два ключевых действия

- **Stubbing (`when...thenReturn`)** — задать, что мок вернёт на вызов. Так мы
  подставляем нужные для теста данные, не поднимая реальную зависимость.
- **Verify (`verify`)** — проверить, что метод мока **был вызван** (с нужными
  аргументами, нужное число раз). Полезно, когда результат — не возврат значения,
  а факт вызова (например, отправка уведомления).

## Виды дублёров

Термины, которые могут спросить:

- **Mock** — заглушка с заданным поведением, на которой ещё и проверяют вызовы.
- **Stub** — просто отдаёт заранее заданные ответы (частный случай).
- **Spy** — обёртка вокруг **реального** объекта: по умолчанию работает
  настоящий метод, но часть можно переопределить. Нужен реже.

## Mockito со Spring и JUnit

Обычно моки создают аннотациями, чтобы не писать `mock(...)` руками:

```java
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
    @Mock  OrderRepository repo;      // создать мок
    @InjectMocks OrderService service; // подставить моки в тестируемый объект
}
```

- `@Mock` — создаёт мок зависимости.
- `@InjectMocks` — создаёт тестируемый объект и **вставляет** в него моки.

В Spring-тестах для подмены бина в контексте используют `@MockBean` (см.
тестирование Spring-приложений).

## Чего не стоит делать

- **Не мокать всё подряд.** Мокают внешние зависимости, а не простые объекты
  данных. Тест, где замокано вообще всё, проверяет моки, а не логику.
- **Не завязываться на детали реализации.** Слишком много `verify` на каждый
  внутренний вызов делает тест хрупким — он падает при любом рефакторинге, хотя
  поведение не изменилось.

## Как ответить на интервью

Коротко: чтобы тестировать класс в изоляции, его зависимости заменяю **моками** —
заглушками с управляемым поведением, для этого Mockito. Два основных действия:
**stubbing** (`when(...).thenReturn(...)`) — задать, что мок вернёт, и **verify** —
проверить, что метод был вызван (когда важен факт вызова, а не возврат). Моки
создаю аннотациями `@Mock` и `@InjectMocks`, в Spring-контексте — `@MockBean`. Есть
ещё spy — обёртка над реальным объектом. Важно не мокать всё подряд и не проверять
каждый внутренний вызов, иначе тест хрупкий и проверяет реализацию, а не поведение.
