# Testcontainers

Testcontainers — библиотека, которая в тестах поднимает **настоящие** внешние
зависимости (PostgreSQL, Kafka, Redis) в Docker-контейнерах. Решает старую
проблему интеграционных тестов: как проверить код на реальной БД, а не на замене,
которая ведёт себя иначе.

## Проблему какую решает

Раньше репозитории тестировали на встроенной **H2**. H2 быстрая, но это **другая**
СУБД: свой SQL-диалект, нет части возможностей PostgreSQL (специфичные типы,
блокировки, оконные функции). Тест на H2 может проходить, а на боевом Postgres —
падать. Получается, тестировали не то, что работает в проде.

Testcontainers поднимает в тесте **тот самый** PostgreSQL нужной версии в
контейнере — тест идёт против реальной СУБД.

## Как это работает

1. В тесте объявляешь контейнер с нужным образом.
2. Перед тестами Testcontainers **запускает** контейнер, отдаёт его адрес и порт.
3. Приложение в тесте подключается к этому контейнеру.
4. После тестов контейнер **останавливается и удаляется** — среда чистая, ничего
   не оставляет за собой.

```java
@Testcontainers
class OrderRepositoryTest {
    @Container
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:16");

    @DynamicPropertySource
    static void props(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }
}
```

`@DynamicPropertySource` подставляет реальные координаты поднятого контейнера в
настройки Spring — приложение подключается к нему автоматически.

## Плюсы и цена

- **Плюс:** тесты идут против **той же** технологии, что в проде — честно и
  надёжно; среда одноразовая и воспроизводимая, не нужно руками поднимать БД.
- **Минусы:** нужен **Docker** на машине и в CI; тесты **медленнее** unit
  (старт контейнера — секунды). Поэтому Testcontainers — для интеграционных
  тестов, а не для каждого теста. Часто контейнер переиспользуют на весь класс/
  прогон, чтобы не поднимать заново.

## Где применяют

- Репозитории и запросы на настоящем PostgreSQL.
- Интеграция с Kafka, Redis, S3 (MinIO) — есть готовые контейнеры под многие
  сервисы.

## Как ответить на интервью

Коротко: Testcontainers поднимает в тестах настоящие зависимости — PostgreSQL,
Kafka, Redis — в Docker-контейнерах. Решает проблему H2: встроенная база быстрая,
но это другой диалект, и тест на ней не гарантирует работу на боевом Postgres.
Testcontainers запускает тот самый Postgres нужной версии в контейнере перед
тестами и удаляет после — среда честная и одноразовая, координаты подставляются в
Spring через `@DynamicPropertySource`. Цена — нужен Docker и тесты медленнее, чем
unit, поэтому это для интеграционных тестов, а логику продолжаю проверять быстрыми
unit с моками.
