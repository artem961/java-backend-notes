# Инструменты трейсинга

Сама идея trace/span не привязана к конкретной библиотеке, но полезно знать названия,
которые встретишь на практике: чем **собирают** трейсы в коде и где их потом
**смотрят**. Глубоко настраивать это junior-у не придётся, достаточно ориентироваться в
терминах.

## Два слоя: сбор и хранение-просмотр

Инструменты делятся на две части:

- **Сбор в приложении (инструментирование)** — библиотека внутри сервиса создаёт спаны,
  проставляет trace ID и пробрасывает его при вызовах. Часто это происходит
  **автоматически** — на входящие HTTP-запросы, вызовы через клиент, запросы в базу
  спаны навешиваются без ручного кода.
- **Хранилище и UI** — отдельная система, куда спаны отправляются и где их смотрят в виде
  дерева. Сюда приходят спаны со всех сервисов и склеиваются по trace ID.

## OpenTelemetry — стандарт сбора

**OpenTelemetry (OTel)** — современный **отраслевой стандарт** сбора телеметрии (трейсы,
метрики, логи). Даёт единый набор библиотек и общий протокол, не привязанный к
конкретному вендору: инструментируешь сервис один раз, а данные можно отправлять в любой
совместимый бэкенд. Сейчас это фактически дефолт для трейсинга.

## Jaeger и Zipkin — хранилище и просмотр

**Jaeger** и **Zipkin** — популярные системы, куда трейсы складываются и где их смотрят.
В их UI можно найти трейс по ID, увидеть дерево спанов и их длительности, найти самый
медленный шаг. Функционально похожи, различаются деталями; Jaeger сейчас встречается
чаще. OpenTelemetry умеет слать данные и туда, и туда.

## В Spring: Micrometer Tracing

В экосистеме Spring Boot за трейсинг отвечает **Micrometer Tracing** (пришёл на смену
Spring Cloud Sleuth). Подключается зависимостью и делает основное **автоматически**:

- генерирует trace ID на входящий запрос, если его ещё нет;
- пробрасывает ID при исходящих вызовах (`RestTemplate`, `WebClient`, Feign);
- **кладёт trace ID в логи** (в MDC), так что он сразу виден в каждой строке;
- отправляет спаны в бэкенд (через OpenTelemetry / в Zipkin).

То есть базовый трейсинг в Spring-сервисе включается в основном конфигурацией, а не
ручным кодом.

## Как ответить на интервью

Коротко: инструменты трейсинга делятся на два слоя — сбор в приложении и
хранилище-просмотр. Сбор сейчас стандартизирует **OpenTelemetry** — отраслевой стандарт
телеметрии, единые библиотеки и протокол, не привязанные к вендору. Смотрят трейсы в
системах вроде **Jaeger** или **Zipkin**: туда приходят спаны со всех сервисов,
склеиваются по trace ID, и в UI видно дерево спанов и самый медленный шаг. В Spring Boot
за это отвечает **Micrometer Tracing** (бывший Sleuth) — он почти всё делает
автоматически: генерирует trace ID, пробрасывает его при вызовах, кладёт в логи и шлёт
спаны в бэкенд. Сам это не настраивал, но знаю, чем собирают и где смотрят.
