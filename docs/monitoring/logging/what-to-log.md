# Что и как логировать

Уметь вызвать логгер мало — важно понимать, **что писать в лог, а что нет**. Плохие логи
одинаково бесполезны и когда их слишком мало (нечего смотреть при инциденте), и когда
слишком много (тонешь в шуме) — а лишнее в логах ещё и опасно с точки зрения
безопасности.

## Что логировать

Ориентир — чтобы по логам можно было **восстановить, что произошло** с запросом:

- **значимые события хода работы** — принят запрос, создан заказ, вызван внешний сервис
  (уровень `INFO`);
- **ошибки — со стек-трейсом**: исключение передают в логгер объектом, а не только его
  текст:

```java
try {
    paymentClient.charge(order);
} catch (PaymentException e) {
    log.error("Не удалось провести оплату заказа {}", order.getId(), e); // e — последним
}
```

  так в лог попадёт полный стек-трейс, по которому видно, **где** упало;
- **контекст**, по которому потом искать: идентификатор заказа, пользователя, запроса.

## Чего логировать нельзя

Отдельно про безопасность — в логи **не должны попадать**:

- **пароли, токены, ключи, номера карт, CVV** — лог не защищён так, как база, и часто
  уезжает в общее хранилище, где его видят многие;
- **персональные данные** — по возможности маскируют;
- **целиком тело запроса/ответа** без разбора — там легко проскочит что-то из
  перечисленного.

Утечка секрета в лог — реальный инцидент безопасности, а не мелочь. Это любят проверять
вопросом «что нельзя писать в лог».

## Структурные логи и MDC

Обычный лог — строка текста, машине её разбирать неудобно. Поэтому в распределённых
системах пишут **структурные логи** — в формате «ключ-значение» (часто JSON): по полям
`level`, `service`, `orderId` централизованная система может искать и фильтровать.

Чтобы не таскать общий контекст (кто, какой запрос) в каждый вызов логгера руками,
используют **MDC (Mapped Diagnostic Context)** — контекст на поток, который автоматически
подставляется в каждую строку лога:

```java
MDC.put("userId", userId);
// дальше все логи в этом потоке будут содержать userId
```

Ключевое применение MDC — **correlation ID / trace ID**: его кладут в MDC на входе
запроса, и он появляется в каждой строке лога этого запроса. Тогда по одному ID
поднимаешь все логи конкретного запроса — в том числе со всех сервисов
(см. [Трейсинг запросов](../tracing/request-tracing.md)). В Spring это делает
Micrometer Tracing автоматически.

## Как ответить на интервью

Коротко: логировать надо так, чтобы по логам можно было восстановить, что случилось с
запросом — значимые события на INFO и ошибки обязательно со стек-трейсом (исключение
передаём в логгер объектом, а не только текст), плюс контекст для поиска: id заказа,
пользователя, запроса. Чего писать нельзя — секретов: паролей, токенов, номеров карт,
персональных данных; утечка секрета в лог — это инцидент безопасности. В распределённых
системах логи делают структурными (ключ-значение, JSON), чтобы централизованно искать по
полям, а общий контекст — прежде всего correlation/trace ID — кладут в **MDC**, тогда он
автоматически попадает в каждую строку, и по одному ID поднимаешь логи запроса со всех
сервисов.
