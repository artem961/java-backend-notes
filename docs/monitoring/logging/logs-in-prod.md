# Логи в продакшене

На своей машине лог смотрят в консоли или в файле. В проде так не выйдет: сервисов много,
у каждого несколько экземпляров, они запускаются и гаснут. Логи из десятков контейнеров
нужно **собрать в одно место**, где по ним можно искать. Это и есть главная особенность
логирования в продакшене.

## Проблема: логи размазаны по экземплярам

Один запрос мог пройти через несколько сервисов, у каждого — по несколько подов. Заходить
на каждый и грепать файл нереально:

- экземпляров десятки, и они **эфемерны** — под пересоздался, локальные логи пропали;
- один запрос оставляет следы **в разных сервисах**;
- искать нужно **по всем сразу**, а не по одному.

Поэтому логи централизуют — собирают со всех экземпляров в общее хранилище с поиском.

## Централизованный сбор

Идея одинаковая у всех решений:

- приложение просто **пишет лог в стандартный вывод** (stdout), не заботясь о доставке;
- **сборщик** (агент рядом) забирает эти строки и шлёт в центральное хранилище;
- в хранилище логи **индексируются**, и по ним есть **поиск и фильтры** (по сервису,
  уровню, correlation ID, времени).

Типовые стеки — **ELK** (Elasticsearch для хранения и поиска, Logstash для обработки,
Kibana для UI) и более лёгкий **Loki** (от авторов Grafana, смотрят логи прямо в
Grafana рядом с метриками). Знать надо не детали, а саму схему «собрали со всех → ищем в
одном месте».

## Приложение просто пишет в stdout

Отсюда правило для контейнеров: приложение **не пишет логи в файлы само** и не крутит
ротацию — оно пишет в stdout, а дальше забота инфраструктуры. Это укладывается в подход
контейнеров (см. [Контейнеры и образы](../../infrastructure/docker/containers-images.md)):
контейнер эфемерен, состояние наружу, логи — поток, который подхватывает платформа. В
Spring Boot по умолчанию так и есть — Logback пишет в консоль.

## Зачем correlation ID именно здесь

В общем хранилище логи всех сервисов и всех запросов **перемешаны**. Вытащить из этой
каши историю одного запроса помогает **correlation ID**: по одному идентификатору
фильтр показывает все строки этого запроса со всех сервисов по порядку. Без него
централизованные логи — просто большая свалка, поэтому trace/correlation ID и логи в
распределёнке всегда идут вместе.

## Как ответить на интервью

Коротко: в проде логи нельзя смотреть на каждой машине — сервисов и экземпляров много,
они эфемерны, а один запрос размазан по нескольким сервисам. Поэтому логи централизуют:
приложение просто пишет в stdout, сборщик забирает и шлёт в общее хранилище с поиском и
фильтрами — типовые стеки ELK (Elasticsearch/Logstash/Kibana) или более лёгкий Loki,
который смотрят прямо в Grafana. Приложение при этом само в файлы не пишет и ротацию не
крутит — пишет в stdout, остальное делает инфраструктура, это и логике контейнеров
соответствует. И чтобы в общей куче найти историю одного запроса, нужен correlation ID —
по нему фильтруешь все строки запроса со всех сервисов; без него централизованные логи
превращаются в свалку.
